# Алгоритм проверки и оценки риска — модуль авторизации (149-ФЗ)

Модуль `auth/` проверяет сайты на соответствие двум новым требованиям
149-ФЗ «Об информации»:

- **Авторизация пользователей через российские сервисы** (ст. 13.55 КоАП РФ,
  введена законопроектом № 1069392-8, принят 09.06.2026)
- **Рекомендательные технологии** (ст. 13.56 КоАП РФ; ст. 10.2-2 149-ФЗ;
  приказ РКН № 149 от 06.10.2023)

Реализация: `auth/checker.py` (логика сканирования), `auth/sources.py`
(база проверяемых паттернов и метаданных).

---

## 1. Этапы проверки одного домена (`scan_site`)

### Шаг 1 — Загрузка главной страницы

URL нормализуется (`_normalize_url`): если протокол не указан, добавляется
`https://`. Затем выполняется GET-запрос с браузерным `User-Agent` и
таймаутом 12 секунд (`REQUEST_TIMEOUT`).

Если страница недоступна (таймаут, сетевая ошибка, HTTP-ошибка) — сканирование
прекращается, результату присваивается `risk = "error"` с сообщением
*«Сайт недоступен или превышен таймаут соединения»*.

### Шаг 2 — Поиск страниц авторизации/регистрации

На главной странице ищутся ссылки, текст или `href` которых содержат
ключевые слова: `login`, `signin`, `register`, `signup`, `auth`, `account`,
`cabinet`, а также русские «войти», «вход», «регистрация», «аккаунт»,
«личный» (`_find_auth_pages`).

Из найденных ссылок отбираются только ведущие на тот же домен, без
дублей и без самой главной страницы. Берётся не более **2 дополнительных
страниц** — итого проверяется максимум **3 страницы** (`MAX_PAGES = 3`):
главная + до 2 страниц входа/регистрации. Каждая дополнительная страница
загружается тем же способом, что и главная; недоступные страницы
пропускаются молча.

### Шаг 3 — Сканирование HTML по regex-паттернам

Для каждой загруженной страницы и для каждой записи из базы `AUTH_SOURCES`
(`auth/sources.py`), у которой задан список `patterns`, выполняется поиск
по регулярным выражениям (`re.IGNORECASE | re.DOTALL`) по полному тексту
HTML-страницы.

Для каждого найденного совпадения вырезается **сниппет** — фрагмент HTML
длиной до 300 символов вокруг места совпадения (по 100 символов в каждую
сторону, `SNIPPET_CONTEXT`), с нормализацией пробелов. На одну проверку
сохраняется **не более 3 уникальных сниппетов**.

Результаты по всем страницам накапливаются в единый словарь по
`entry_id` — если паттерн сработал на нескольких страницах, все они
попадают в список `pages` этой проверки, а сниппеты объединяются
(без дублей, тоже не более 3).

### Шаг 4 — Анализ рекомендательных технологий

Независимо от базы `AUTH_SOURCES`, по тексту всех загруженных страниц
ищутся три группы признаков:

| Признак | Что ищется | Регулярки (примеры) |
|---|---|---|
| `has_rec_tech` | Алгоритмы персонализации на сайте: рекомендации, «похожее», «вам может понравиться» | `рекомендуем\|рекомендации\|вам\s+может\s+понравиться`, `recommend\|similar\s+items\|персонализир`, `collaborative[\s_-]?filtering` |
| `has_rec_disclosure` | Уведомление пользователей о применении рекомендательных технологий | `рекомендательн[а-я]+\s+технолог`, `применяются\s+рекомендательные`, `recommendation[\s_-]?technolog` |
| `has_rec_rules_doc` | Ссылка/упоминание документа «Правила применения рекомендательных технологий» | `правила\s+применения\s+рекомендательн`, `rules[\s_-]?of[\s_-]?recommendation`, `/rec[\s_-]?rules` |

Каждый признак проверяется по всем страницам; флаг становится `True`,
как только сработал хотя бы один паттерн на любой из страниц.

### Шаг 5 — Проверки на ОТСУТСТВИЕ (негативные проверки)

Если алгоритмы персонализации обнаружены (`has_rec_tech == True`), но:

- **нет уведомления** (`has_rec_disclosure == False`) → добавляется
  нарушение `rec_tech_disclosure` (риск `high`)
- **нет документа правил** (`has_rec_rules_doc == False`) → добавляется
  нарушение `rec_tech_rules_doc` (риск `high`)

Это единственные две записи в базе с флагом `absence_check = True` —
для них логика «найдено = нарушение» инвертирована: нарушением является
именно **отсутствие** требуемого элемента при наличии признаков
рекомендательных алгоритмов. Если `has_rec_tech == False`, обе проверки
пропускаются — сайт без персонализации не обязан публиковать эти документы.

### Шаг 6 — Формирование списка hits

Для каждой записи из базы, по которой было найдено совпадение на шаге 3
(`accumulated`), в зависимости от категории:

- **`auth_allowed`** (разрешённые методы авторизации — SMS, Госуслуги/ЕСИА,
  Яндекс ID, Сбер ID, VK/OK) → добавляется в `allowed_auth_found` (список
  названий) и в `hits` с `is_present = True`. Это «положительные» находки,
  штрафы к ним не относятся.

- **`auth_foreign`** (иностранные сервисы авторизации) и **`rec_tech`**
  (с `absence_check = False`, т.е. кроме двух записей из шага 5) →
  добавляется в `hits` с `is_present = True` как нарушение.

Записи с `absence_check = True` (две rec_tech-проверки) на этом шаге
**пропускаются** — они уже обработаны на шаге 5 как «найдено = ОК,
отсутствие = нарушение».

### Шаг 7 — Итоговый уровень риска домена

Из всех `hits` отбираются **нарушения** — записи категорий
`auth_foreign` и `rec_tech` (независимо от `is_present`, но на практике
к этому моменту в `hits` остаются только релевантные записи).

Итоговый `risk` определяется по принципу «худший из найденных»:

```
если есть хотя бы одно нарушение с risk == "critical"  → risk = "critical"
иначе если есть хотя бы одно с risk == "high"           → risk = "high"
иначе если есть хотя бы одно с risk == "medium"         → risk = "medium"
иначе если нарушения есть (но все risk == "low")        → risk = "low"
иначе (нарушений нет)                                   → risk = "clean"
```

На данный момент в базе **нет записей с уровнем `medium`** — это
зарезервированная ступень шкалы для будущих проверок. Текущие уровни риска
по записям:

| Уровень | Записи |
|---|---|
| `critical` | Google OAuth, Apple ID, Microsoft Account/Azure AD, Facebook Login (Meta) |
| `high` | GitHub OAuth, иностранная email-почта как идентификатор, Discord OAuth, отсутствие уведомления о рекомендательных технологиях, отсутствие документа правил |
| `low` | все записи категории `auth_allowed` (SMS, Госуслуги/ЕСИА, Яндекс ID, Сбер ID, VK/OK) — это разрешённые методы, а не нарушения |
| `clean` | присваивается результату, если в `hits` нет ни одной записи категорий `auth_foreign`/`rec_tech` |
| `error` | сайт недоступен (шаг 1) |

> Важно: уровень `low` у записей `auth_allowed` **не влияет** на финальный
> риск сайта в сторону повышения — на шаге 7 в расчёт берутся только
> категории `auth_foreign` и `rec_tech`. Если сайт использует, например,
> только Госуслуги и SMS-авторизацию и не найдено других нарушений,
> итоговый риск будет `clean`, даже если в `hits` присутствуют записи
> с `risk == "low"`.

## 2. Структура одной проверочной записи (`AuthEntry`)

Каждая запись в `auth/sources.py` описывает один проверяемый признак:

| Поле | Назначение |
|---|---|
| `id` | Уникальный идентификатор (например, `google_oauth`) |
| `name` | Человекочитаемое название |
| `category` | `auth_foreign` \| `rec_tech` \| `auth_allowed` |
| `risk` | `critical` \| `high` \| `medium` \| `low` |
| `description` | Описание сути нарушения/соответствия |
| `legal_basis` | Статья закона |
| `fine_range` | Диапазон штрафов |
| `advice` | Рекомендация по устранению |
| `patterns` | Список regex для поиска в HTML |
| `absence_check` | `True`, если «найдено» означает соответствие, а «не найдено при наличии предпосылок» — нарушение (используется только для двух rec_tech-записей) |

## 4. Известные ограничения (ponytail-заметки)

- **Регулярки, не парсинг DOM.** Поиск идёт по сырому HTML целиком
  (включая атрибуты, JS-инлайны, комментарии). Это даёт высокую
  чувствительность, но может давать **ложноположительные** срабатывания
  (например, упоминание «gmail.com» в тексте статьи, а не в форме входа).
  При росте базы — рассмотреть переход на анализ DOM через BeautifulSoup
  для критичных проверок (кнопки, формы).

- **До 3 страниц на домен.** Если формы авторизации находятся глубже
  (например, в SPA за JS-роутингом без серверных ссылок), они не будут
  обнаружены без Playwright. В 152-ФЗ-модуле для аналогичных случаев уже
  используется Playwright — при необходимости можно интегрировать тот же
  подход и здесь.

- **Уровень `medium` зарезервирован**, но не используется ни одной
  записью — при добавлении новых проверок среднего риска шаг 7 уже
  поддерживает эту ступень без изменений кода.

- **`has_rec_tech`/`has_rec_disclosure`/`has_rec_rules_doc`** определяются
  по ключевым словам по всему HTML — формально достаточно одного слова
  «рекомендуем» где угодно на странице, чтобы сайт считался применяющим
  рекомендательные технологии. Это намеренно консервативный (избыточный)
  подход — лучше ложное предупреждение, чем пропущенное нарушение с
  штрафом до 700 000 руб.
